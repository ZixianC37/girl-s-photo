# GraphRAG 写真行业知识系统设计

## 概述

为写真行业构建 GraphRAG 系统，覆盖归因分析、智能问答、客服、决策辅助四大场景。采用分阶段迭代策略，以数据驱动的方式并行推进知识学习与数据准备。

## 业务场景

- **归因分析** — 关联客户、订单、产品、门店等多个实体，回答业绩波动原因
- **智能问答** — 多跳查询客户历史、产品信息、订单状态
- **客服** — 自动回答客户咨询（如"我上次拍的什么风格？"、"有没有适合XX场景的产品？"），减少人工客服工作量
- **决策辅助** — 基于知识图谱的数据洞察，支持产品和运营决策

## 方案选择

选择**方案B：并行学习+数据准备**，理由：

- 避免理论学习脱离实际数据，知识-数据映射更准确
- 视频学习与数据分析同步推进，效率更高
- 学习过程中提炼的实战 skill 可以直接针对实际数据验证

## 整体阶段路线

### 阶段0：并行准备期

**输入：**
- 用户提供 GraphRAG 相关视频链接（B站/YouTube）
- 用户导出飞书数据表格（CSV/Excel）

**视频知识学习流程：**

1. 抓取视频页面 — 提取标题、简介、字幕/文字稿
2. 知识归纳 — 整理为结构化文档：
   - GraphRAG 核心概念（实体、关系、社区、查询策略）
   - 技术栈选型对比（Neo4j vs Nebula、LlamaIndex vs LangChain 等）
   - 实战落地步骤拆解
   - 常见坑和最佳实践
3. 提炼实战 Skill — 每个关键落地环节提炼为一个 skill：
   - Skill 名称（如 `graph-schema-design`、`entity-extraction-pipeline`）
   - 输入定义、输出定义、执行检查清单、质量验收标准
   - 示例：`graph-schema-design` — 输入：数据映射文档 + 实体列表；输出：Neo4j Cypher Schema；检查清单：所有实体有标签、所有关系有方向和类型、属性有索引

**飞书数据分析流程：**

1. 数据概览 — 每张表的字段、数据量、数据类型
2. 实体识别 — 从字段名和数据内容识别潜在实体
3. 关系推断 — 表间和表内的潜在关系
4. 数据质量评估 — 缺失值、重复、不一致等问题

**产出：知识-数据映射文档**

此文档用于指导阶段1的图谱 Schema 设计和实体提取流程，将飞书原始数据与 GraphRAG 概念对齐。

| 飞书数据表 | 实体/关系类型 | GraphRAG 用途 | 处理 Skill | 优先级 |
|-----------|-------------|-------------|-----------|-------|
| 客户信息表 | Customer 实体 | 智能问答、客服 | entity-extraction-pipeline | P0 |
| 订单表 | Order 实体 + (Customer)-[PLACED]->(Order) 关系 | 归因分析 | entity-extraction-pipeline | P0 |
| 产品表 | Product 实体 | 决策辅助 | graph-schema-design | P1 |

映射文档中必须包含从视频学习中提炼的实战落地 skill，用于后续阶段的执行约束。

### 阶段1：PoC 原型验证

**范围：**
- 选 2-3 张最核心的飞书表
- 构建 mini 知识图谱 + 基础检索链路
- 验证场景：阶段0完成后根据数据情况决定（归因分析 或 智能问答优先）

**技术选型（初步）：**

| 组件 | 推荐选型 | 备选 | 理由 |
|------|---------|------|------|
| 图数据库 | Neo4j (Community) | NebulaGraph | 生态成熟，文档丰富，社区版免费 |
| RAG 框架 | LlamaIndex | LangChain | GraphRAG 支持更原生 |
| LLM | Claude API (Sonnet) | GPT-4 | 性价比好 |
| 向量数据库 | Chroma | Milvus, Qdrant | PoC 阶段轻量即可 |
| 数据处理 | Python + Pandas | — | GraphRAG 工具链主要在 Python 生态 |

**里程碑（由阶段0提炼的 skill 驱动）：**

- M1: 数据建模 & 图谱 Schema 设计
- M2: 数据导入 & 实体/关系提取
- M3: 查询引擎搭建
- M4: 对比验证 — GraphRAG vs 传统 RAG（评估维度：回答准确率、多跳推理完整性、可解释性）

**验收标准：** 由阶段0提炼的 skill 定义。兜底标准：知识图谱包含至少 3 种实体类型、5 种关系类型，能回答至少 5 个需要多跳推理的真实业务问题。

### 阶段2：场景扩展

方向性描述，阶段1完成后细化：
- 逐步纳入更多飞书数据表（总计 30+ 张）
- 扩展到客服、决策辅助等场景
- 具体计划在阶段1完成后制定

### 阶段3：工程化与集成

方向性描述，阶段2完成后细化：
- API 设计与部署
- 与飞书机器人等现有系统集成
- 具体计划在阶段2完成后制定

## 执行约束机制

### Skill 提炼机制
- 从视频学习中提取的关键实战环节 → 每个提炼为独立 skill
- 每个 skill 包含：输入定义、输出定义、执行步骤、检查清单、质量验收标准
- Skill 存放在项目 `.claude/skills/` 目录下，同时在 `docs/skills/` 保留可读副本

### 检查点机制
- 每个阶段结束前回顾：目标达成度、遗留问题、下阶段调整
- 关键决策点记录在设计文档中

### 质量守则
- 数据清洗步骤不跳过
- 图谱 Schema 设计经过评审
- 每个 milestone 完成后验证效果

## 用户技术背景

- 有 LLM API 调用经验（Python）
- 无图数据库和 RAG 框架经验
- 从产品经理视角驱动，重视可验证的效果

## 风险

1. **视频文字稿质量** — B站/YouTube 字幕获取可能不完整，需用户补充关键笔记
2. **30+ 表数据清洗** — 工作量大，需分优先级处理。缓解：阶段1先处理 2-3 张核心表，按业务价值排序优先级
3. **图谱质量** — 实体/关系提取的准确率直接影响最终效果，需迭代优化
4. **实体关系歧义** — 真实业务数据中实体角色可能存在歧义（如客户同时是购买者和推荐人），需在 Schema 设计时明确关系语义
5. **冷启动问题** — 无已有图 Schema 参考，初始设计可能需要多次迭代重构。缓解：阶段0充分学习后再设计，保留 Schema 版本化
