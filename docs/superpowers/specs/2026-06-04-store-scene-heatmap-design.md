# 门店场景热力图 MVP 设计规格

**Date:** 2026-06-04
**Status:** Approved
**Version:** MVP v1 — 门店视角，先做出来看效果

## 概述

在飞书多维表的数据基础上，开发一个门店场景利用率热力图。以门店视角展示每个物理场景（影棚/房间）的业务数据，让管理者和门店一眼看到场景冷热分布，解决"产品方案场景分配不合理"的核心问题。

## 需求背景

### 问题
- 产品研发做方案时没有考虑场景分配合理性
- 热门场景过载（堵景）、冷门场景闲置，缺乏全局视角
- 研发、门店、管理三方看不到场景利用的真实数据

### 根因（四位专家共识）
1. **信息不足（50%）**：研发做方案时看不到各场景的当前负荷
2. **流程缺失（30%）**：8阶段研发流程中没有"场景冲突检查"环节
3. **缺乏整体规划（20%）**：没有"每店每景的合理承载量"定义

### MVP 策略
先展示数据，再迭代逻辑。不定义复杂的堵景指数/阈值算法，把真实业务数据铺到场景上，让各方看到现状后形成共识。

## 设计决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 视角 | 门店视角（MVP） | 先解决最核心的"门店看到自己场景状态"的需求 |
| 热力逻辑 | 直接展示业务数据 | 先不定义堵景算法，让数据说话 |
| 平台 | 飞书多维表（数据）+ 独立网页（展示） | 先做出来看效果，嵌入方式后定 |
| 技术方案 | ECharts + 飞书 Bitable API | 最轻量，3-5天可完成 |
| 场景范围 | 5家已细分场景的门店 | 麦芽岛滨江和甜熊余杭只有1个选项，第一版跳过 |

### 数据注意事项
- 影棚字段混用单选和多选，聚合时需分别处理
- 多选字段需"展开"计数（每个选项各+1）
- 2133条记录，API分页5次拉取，约2-4秒加载

### 技术栈

- 前端：HTML + JavaScript + ECharts（CDN）
- 后端：Python FastAPI（现有中台项目）
- 数据源：飞书 Bitable REST API
- 部署：先本地运行，后续嵌入飞书

### API 数据流

1. 前端请求中台 API `/api/heatmap/{store_id}`
2. 中台从飞书 Bitable API 拉取执行output表数据（分页5次）
3. 中台做聚合计算：按门店→场景分组，统计使用次数、产品数、上新数
4. 返回聚合后的 JSON 给前端
5. 前端用 ECharts 渲染热力图

## 实施步骤

### 第一步：搭建飞书应用 + API 验证（1天）
1. 飞书开放平台创建企业自建应用
2. 申请 bitable:app 权限
3. 获取 app_token 和 table_id
4. 验证 API 可通

### 第二步：中台 API 开发（1-2天）
1. 中台项目新增热力图 API 路由
2. 实现 Bitable API 代理（认证 + 分页拉取）
3. 实现场景数据聚合逻辑
4. 返回结构化 JSON

### 第三步：前端热力图开发（1-2天）
1. 创建 HTML 页面，引入 ECharts CDN
2. 实现场景卡片网格布局
3. 实现门店切换和筛选
4. 实现场景详情弹窗
5. 本地测试验证

### 第四步：联调测试（0.5天）
1. 前端连接中台 API
2. 用真实数据验证
3. 修复 bug
