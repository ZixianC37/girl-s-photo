# 任务分发中台设计

## 背景

写真产品研发部门面临两个实际问题：
1. **触达率低**：员工不习惯查看飞书等业务系统通知，任务分配后触达不到位
2. **回收闭环做不到**：任务确认、文件提交、进度跟踪缺乏有效手段，需要反复催促

公司已有完善的飞书多维表格体系作为数据层，沉淀了产品数据和业务流程。本系统在飞书数据层之上，构建一个中台服务，以钉钉群和单聊作为触达渠道，实现任务的下发、确认、文件收集、进度跟踪和自动催办。

## 核心场景

### 场景1：品鉴会任务（会议/活动类）

管理员在飞书多维表新增一条品鉴会记录（名称、时间、参会人列表、截止时间、材料要求），系统自动在钉钉群发送互动卡片任务，参会人点击确认后在单聊中上传准备材料，系统自动收集文件、跟踪进度、超时催办。

### 场景2：产品研发流程任务

在7阶段SOP的关键节点（如样片评审、上市前准备等），系统自动下发任务给对应负责人，收集交付物并跟踪完成状态。

## 成功指标

- **任务触达率**：任务下发后24h内确认率 ≥ 90%（基线待确认）
- **文件回收率**：截止时间前文件提交率 ≥ 80%
- **催办效率**：自动催办后24h内响应率 vs 人工催办响应率
- **用户满意度**：使用该系统的员工反馈评分（问卷）

具体基线需在阶段1启动前通过飞书历史数据计算。

## 设计原则

1. **飞书为主数据源，中台为运行时层**：业务主数据（任务、人员、状态）存储在飞书多维表；中台只存储运行时数据（消息映射、文件索引、调度状态）
2. **群聊触达，单聊收文件**：利用钉钉群聊的互动卡片做任务分发和进度展示，利用单聊做文件收集（群聊不支持文件接收）
3. **架构-场景分离**：中台是通用的事件路由和任务引擎，具体业务场景通过配置驱动，不硬编码业务逻辑

## 系统架构

### 三层结构

```
┌──────────────────────────────────────────────────┐
│                   触达层（钉钉）                    │
│  群聊：互动卡片任务 / 进度看板 / @提醒              │
│  单聊：文件收集 / 个性化引导                        │
├──────────────────────────────────────────────────┤
│                   中台服务                         │
│  事件总线 / 身份映射 / 任务引擎 / 文件管理 / 定时催办 │
│  ┌─────────────────────────────────────────┐      │
│  │           中台数据库                      │      │
│  │  消息ID映射 / 文件索引 / 调度状态 / 日志   │      │
│  └─────────────────────────────────────────┘      │
├──────────────────────────────────────────────────┤
│                   数据层（飞书多维表）               │
│  业务主数据：任务记录 / 人员信息 / 任务状态           │
└──────────────────────────────────────────────────┘
```

### 数据流向

**下行（飞书→钉钉）**：飞书新增/更新记录 → 飞书自动化webhook → 中台事件网关 → 身份映射 → 钉钉API发送互动卡片/消息

**上行（钉钉→飞书）**：用户点击按钮/发送文件 → 钉钉回调 → 中台处理 → 飞书API更新记录

**定时（中台主动）**：催办调度器定期扫描 → 检查截止时间 → 发送催办消息

## 任务生命周期

以品鉴会场景为例：

```
1. 创建：管理员在飞书多维表新增品鉴会记录
        （字段：名称、时间、参会人列表、截止时间、材料要求）
        ↓
2. 触发：飞书自动化webhook → 中台事件总线
        ↓
3. 身份映射：飞书参会人ID → 钉钉用户ID
        ↓
4. 下发：中台通过钉钉API
        a) 在目标群发送互动卡片（任务详情 + "确认参加"按钮）
        b) 卡片中@所有参会人
        ↓
5. 确认：参会人点击"确认参加"
        → 钉钉回调 → 中台处理 → 卡片原地更新进度
        → 中台回写飞书：该参会人状态=已确认
        ↓
6. 引导上传：确认后，中台主动私聊参会人
        "请在本次对话中发送你的品鉴会准备材料"
        ↓
7. 文件收集：参会人在单聊中发送文件/图片
        → 钉钉回调 → 中台下载文件 → 存储到OSS
        → 中台回写飞书：文件索引链接
        → 群聊卡片更新 "张三已提交 ✓"
        ↓
8. 催办：中台定时检查
        - 距截止时间50%未确认 → 私聊提醒
        - 距截止时间24h未确认 → 群内@提醒
        - 已逾期 → 升级通知（通知创建者）
        ↓
9. 完成：所有参会人已提交
        → 群聊卡片更新为"全部完成"
        → 飞书记录状态更新为"已完成"
```

### 任务状态机

任务有两层状态：**任务级状态**（整体进度）和**个人级状态**（每个参会人的确认/提交状态）。

**任务级状态**（存储在飞书任务表）：

```
待下发 → 进行中 → 已完成
                → 已逾期（可恢复：逾期后仍可提交，标记为"逾期提交"）
```

**个人级状态**（存储在中台数据库，定期同步到飞书提交记录表）：

```
未响应 → 已确认 → 已提交（文件已收）
未响应 → 已拒绝（可选，需管理员跟进）
```

任何人可以从任何催办状态回到确认/提交状态。催办不是一个独立状态，而是基于"未响应"或"已确认未提交"触发的动作。

## 中台核心组件

### 1. 事件网关（Event Gateway）

接收外部事件，验签、去重、路由。

输入源：
- 飞书多维表自动化 webhook（记录新增/更新）
- 钉钉互动卡片回调（按钮点击）
- 钉钉消息回调（单聊文件接收）

处理流程：
1. 验证请求签名
2. 基于事件唯一ID去重（防止重复处理）
3. 根据事件类型路由到对应处理器（任务创建/确认/文件收集）

#### 飞书 webhook 集成详情

飞书多维表格自动化配置：
- 触发条件：当多维表格中新增记录时
- 动作：发送 webhook（HTTP POST）到中台
- Payload 示例结构：
  ```json
  {
    "event": {
      "app_id": "cli_xxx",
      "table_id": "tblxxx",
      "record_id": "recxxx",
      "action": "create"
    },
    "data": {
      "fields": {
        "任务标题": "5月竞品品鉴会",
        "参会人列表": [{"id": "feishu_uid_xxx"}],
        "截止时间": 1748000000000
      }
    }
  }
  ```
- 注意：飞书自动化webhook的payload格式可能只包含记录ID而非完整字段数据。中台需要根据record_id回调飞书API获取完整记录内容。
- 飞书API：使用 `GET /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/{record_id}` 获取记录详情
- 认证：使用飞书应用 tenant_access_token（通过 app_id + app_secret 换取）

#### 钉钉回调集成详情

中台需要注册三类钉钉回调URL：
1. **互动卡片回调**：用户点击卡片按钮时触发。在钉钉开放平台注册回调地址，使用 Stream 模式或 HTTP 模式接收。回调payload包含 cardBizId、用户ID、按钮action值。
2. **机器人消息回调**：用户单聊发送文件时触发。使用企业内部应用机器人的消息接收功能。
3. **审批回调**（P2阶段）：审批状态变更时触发。

互动卡片创建使用钉钉开放平台API：
- 创建卡片：`POST /v1.0/card/instances`（设置 cardBizId 用于后续更新）
- 更新卡片：`PUT /v1.0/card/instances`（通过 cardBizId 原地更新内容）
- 回调注册：`POST /v1.0/card/callbackUrls`

### 2. 身份映射服务（Identity Mapper）

维护飞书用户ID与钉钉用户ID的映射关系。

映射方式：
- 首选：通过手机号自动匹配（两个平台的企业通讯录通常共享手机号）
- 备选：手动配置映射表

初始化流程：
1. 调用飞书通讯录API获取用户列表（含手机号）
2. 调用钉钉通讯录API获取用户列表（含手机号）
3. 按手机号自动匹配生成映射关系
4. 未匹配的手动补充

持续同步：
- 启动时全量同步一次
- 每24小时增量同步（检查新入职/离职员工）
- 提供手动触发同步的管理接口
- 映射失败时在任务下发流程中明确提示，不静默跳过

### 3. 任务引擎（Task Engine）

管理任务的状态流转和业务逻辑。

职责：
- 接收飞书新增记录事件，解析任务字段
- 调用钉钉API创建互动卡片消息
- 处理用户确认回调，更新任务状态
- 联动文件管理器和催办调度器

#### 钉钉目标群确定逻辑

任务下发时，中台需要确定发送到哪个钉钉群。策略：
1. **飞书任务表中指定**：在飞书任务表新增"目标钉钉群"字段，创建任务时选择（下拉选项，预配置可用的群列表）
2. **按任务类型自动映射**：中台配置文件中定义规则，如"品鉴会类型 → 钉钉群A"，"产品评审 → 钉钉群B"
3. **创建新群**（后续扩展）：中台自动创建钉钉群并拉入参会人

推荐方案1（飞书表中指定），灵活且创建人可控。

### 4. 文件管理器（File Manager）

处理钉钉单聊中的文件接收和存储。

流程：
1. 接收钉钉文件消息回调（包含 downloadCode）
2. 调用钉钉"下载机器人接收消息的文件内容"API：`POST /v1.0/robot/messageFiles/download`（使用机器人 access_token，传入 downloadCode 和消息所属的 robotCode）
3. 存储到文件存储（OSS或本地）
4. 生成文件访问URL
5. 回写飞书多维表：在提交记录中添加文件链接
6. 通知任务引擎更新卡片状态

文件大小限制：钉钉机器人接收文件最大约 20MB，超过需引导用户使用其他方式提交。

### 5. 催办调度器（Reminder Scheduler）

定时扫描未完成任务，按规则发送催办。

催办规则：
| 条件 | 动作 |
|---|---|
| 距截止时间超过50%，未确认 | 钉钉单聊私聊提醒 |
| 距截止时间不足24h，未确认 | 群内@该参会人 |
| 已逾期，仍未确认 | 通知任务创建者（升级） |
| 已确认但未提交文件，距截止不足24h | 单聊提醒提交文件 |

防骚扰：同一用户同一任务每天最多催办2次。

## 错误处理

| 场景 | 处理方式 |
|---|---|
| 钉钉API调用失败（限流/网络） | 指数退避重试，最多3次，失败后记录日志并通知管理员 |
| 用户在群里直接发文件 | 机器人回复提示"请在与我的私聊中发送文件" |
| 飞书webhook丢失 | 中台定时轮询飞书多维表做补偿同步（每5分钟） |
| 同一任务重复触发 | 事件网关基于飞书记录ID做幂等去重 |
| 用户在截止时间后提交 | 仍然接收，标记为"逾期提交" |
| 身份映射缺失 | 跳过该人，在群里提示管理员补充映射关系 |

## 中台↔飞书数据同步机制

### 中台回写飞书

中台通过飞书开放平台API写入多维表数据：
- API：`PUT /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/{record_id}`
- 认证：使用应用 tenant_access_token
- 写入场景：
  - 用户确认参加后：更新提交记录表的确认状态
  - 文件收集后：在提交记录表添加文件URL
  - 任务完成/逾期：更新任务表的状态字段

### 补偿同步（飞书→中台）

由于webhook可能丢失，中台需要定时补偿：
- 每5分钟轮询飞书多维表，查询"最近创建/更新时间 > 上次轮询时间"的记录
- 与中台本地状态对比，处理差异
- 去重：基于飞书记录ID，跳过已处理的记录
- 冲突处理：以飞书数据为准（飞书是Source of Truth）

## 消息发送队列与限流策略

钉钉API有频率限制（20条/分钟），批量下发时需要队列：
- 下发任务时，参会人消息加入发送队列
- 队列以15条/分钟的速率消费（留buffer给催办等消息）
- 单个任务的下发完成时间 = 参会人数 × (60/15)秒
- 队列持久化到中台数据库，服务重启后继续

## 安全考虑

- API凭证管理：飞书和钉钉的 app_id/app_secret/tenant_token 使用环境变量注入，不写入代码或数据库
- 文件存储访问：OSS/本地存储的文件URL使用签名链接，设置过期时间（默认7天）
- 手机号存储：用户映射表中的手机号仅在匹配时使用，后续操作只使用平台用户ID
- 通信加密：中台与飞书/钉钉的所有通信使用HTTPS
- 内网部署：中台服务仅对内网暴露，webhook回调URL使用内网穿透或固定出口IP

## 与能力复制系统的关系

本系统与"写真产品研发能力复制系统"（见 `2026-05-25-photo-product-rd-capability-replication-design.md`）互补：
- 能力复制系统：提供7阶段SOP框架和知识库，驱动工作流引导
- 本系统：负责任务的触达、收集、跟踪环节
- 集成点：能力复制系统在SOP关键节点触发任务时，通过飞书多维表创建记录，本系统负责将任务推送到钉钉并管理回收闭环

## 前置假设与前提条件

1. 公司已部署钉钉，且目标员工有钉钉账号
2. 飞书多维表已配置自动化webhook能力
3. 中台服务有稳定的部署环境（服务器或容器）
4. 钉钉开放平台已注册企业应用，获取了API调用权限
5. 飞书开放平台已获取多维表读写权限

## 阶段规划

| 阶段 | 范围 | 交付物 |
|---|---|---|
| P0：中台骨架 | 事件网关 + 身份映射 + 基础路由 | 能接收多源事件、做路由转发的最小后端 |
| P1：飞书→钉钉群 | 品鉴会/任务下发场景 | 飞书记录触发 → 钉钉群互动卡片下发 |
| P2：跟踪催办 | 进度跟踪 + 自动催办 + 文件收集 | 完整的任务闭环（下发→确认→收集→催办→完成） |

## 钉钉平台关键限制

| 限制项 | 具体值 | 影响 |
|---|---|---|
| 自定义机器人发送频率 | 20条/分钟 | 需控制下发节奏 |
| 标准版API调用额度 | 10,000次/月 | 可能需要升级专业版（9,800元/年） |
| 群聊文件接收 | 不支持 | 文件收集必须走单聊 |
| 单聊文件接收 | 支持（downloadCode方式） | 文件收集的唯一途径 |
| 互动卡片动态更新 | 支持（cardBizId） | 用于原地更新任务进度 |
